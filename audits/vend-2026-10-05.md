# vend — code audit, 2026-10-05

Scope: the tree at `acc72f2` (`main`). Lens: can a buying agent get a payable XNO quote out of
this server and have its payment judged correctly?

Baseline, before any change, in a clean virtualenv carrying `pyproject.toml`'s own dependency
list:

```
$ python -m pytest -q      # 13 failed, 227 passed, 2 skipped
```

The 13 are the same 13 the 2026-10-03 audit documented: the container's network policy answers
`403 Forbidden` for the external hosts they fetch (`test_cdp_verify::test_validate_endpoint_keyless`,
`test_links_endpoint` ×2, `test_paid_response` ×4, `test_pdf_extract`, `tests/test_wiki_summary` ×5,
`test_cdp_verify`). Not code, and not fixable from here.

## Found and fixed — the USDC handler took the XNO quote down with it

`build_402_challenge` builds the 402 an agent needs in order to pay. It always puts the Nano
accept in the array first, then adds a USDC-on-Base accept when `VEND_USDC_ADDRESS` is set, and
wraps that in `except Exception` — precisely so a USDC problem degrades to the XNO sale that is
already in hand:

```python
    try:
        from cdp_verify import build_usdc_accept
        ...
        accepts.append(usdc_entry)
    except Exception:
        log = logging.getLogger("vend")      # nano_verify.py:556
        log.warning("Failed to build USDC accept for %s", endpoint_path, exc_info=True)
```

**`nano_verify.py` never imported `logging`.** The handler's own first statement raised
`NameError`, so the handler did the opposite of its job: instead of dropping the USDC accept and
returning the challenge, it propagated out of `build_402_challenge` and out of
`format_402_response`. The 402 was never built, so the Nano accept never reached the wire and
**no agent could pay in XNO at all** on a server with the USDC address configured.

Measured against the unfixed tree:

```
$ VEND_USDC_ADDRESS=0x11…11  python -c "...build_402_challenge(...)"
NameError -> name 'logging' is not defined
```

The trigger is anything that makes the USDC accept fail: `from cdp_verify import
build_usdc_accept` raising `ImportError` on a checkout without the CDP dependencies, a malformed
`VEND_USDC_ADDRESS`, or any upstream change to `build_usdc_accept`'s signature. Each of those is
designed to be survivable and each one instead removed the XNO rail.

**Fixed** with the missing `import logging`, and the handler now carries a comment saying what it
is for, so the next edit does not quietly re-lose it.

Four laws in `test_cdp_verify.py`, all failing on the unfixed tree:

```
FAILED test_a_failed_usdc_accept_still_leaves_a_payable_nano_challenge
       E  NameError: name 'logging' is not defined     nano_verify.py:556
FAILED test_the_usdc_handler_logs_instead_of_raising

They cover the builder, the base64 header the server actually puts on the wire

## Checked and clean

- **Raw arithmetic on the price is exact.** `_price_to_raw` goes through `Decimal(str(price))`,
  with the comment naming the drift it avoids (`int(0.0001 * 10**30)` ==
  `100000000000000004764729344`). The quoted price and the enforced price are derived from the
  same `PRICE_RAW`, so they cannot disagree.
- **`verify_payment` fails closed on an unreadable amount.** `int(amount_raw)` and
  `int(expected_amount_raw)` are both inside the `try`, and a parse failure returns
  `valid: False` rather than falling through with the comparison unrun — the comment records
  that swallowing it once "bought an unlimited number of paid calls for nothing".
- **The destination is compared in the right form.** `contents.link_as_account or contents.link`,
  not the bare `link` hash, so a valid payment is not rejected and a payment to someone else is.
- **An unreachable RPC is not a sale.** `check_block_exists` returning `None` yields
  "ledger RPC unreachable" with `valid: False`, not a 500 and not a pass.
- **Replay is impossible.** `store.claim` inserts the block hash as a `PRIMARY KEY` and returns
  `False` if it was spent on any previous call, so one payment buys one call.
- **`parse_block_hash` is the single entry point for payment headers** and accepts only 64-hex,
  bare or inside base64 JSON under a known key. Arbitrary text is refused.
- **No secret in the tree.** `secret_patterns.py` exists for this and the scan is clean; no seed,
  key or token value appears in a tracked file.

## Found, not fixed — reported instead

- **Confirmation is claimed but not checked.** `wait_for_confirmation`'s own docstring says it
  polls "until *block_hash* is a **confirmed**, on-ledger block", and then treats
  `"contents" in info` as confirmed — `block_info`'s `confirmed` field is never read, in this
  file or in `server.py`. An on-ledger-but-unconfirmed send can still be forked away by the payer
  who signed it, so a payment is being treated as final before the network says it is. Not
  carried here: deciding how long to wait and what to tell a buyer meanwhile is a judgement about
  the product, and it is a different concern from the crash above. **This is the one finding on
  this repository that still needs a decision.**
- **`confirm_signature_payment`'s docstring oversells step 2.** It says it will "fast-fail on
  destination mismatch and on a bad decrement amount", but nothing calls
  `block_decrement_amount` before broadcasting — the amount is only checked afterwards, by
  `verify_payment` on the now-on-ledger block. The outcome is still correct (a short payment is
  refused), so this is a docstring that overstates the code rather than a defect; left as a note
  because `block_decrement_amount` is dead code today and a later reader may assume it runs.
- **`raw_to_xno` carries a raw amount through a float** (`val / 1e30`, `:.6f`). It is used only
  to build human-readable messages, never to decide anything, and a sub-microXNO amount therefore
  prints as `0.000000`. Display only; not on the decision path.

## Could not verify

- **Against a real Nano node or the live deployment.** No socket reached either; this container's
  proxy answers 403 for the external hosts. `VEND_ACCOUNT` (`NANO_AGENT_ACCOUNT`) is unset here,
  so `payTo` reads empty in a locally built challenge — the new laws assert the Nano accept's
  presence, asset, scheme and amount, which do not depend on it.
- **Whether `VEND_USDC_ADDRESS` is set in production.** That is what decides whether the crash
  above was live or latent. It is an environment variable on the deployment, not readable from
  here.
- **The 13 pre-existing failures** were confirmed identical before and after, but their
  underlying endpoints were not exercised against the real hosts.

# vend — second audit pass, 2026-10-05 (the buyer-reported defect)

The pass above read the seller's side of the 402. This one starts from the only outside bug
report this repository has: **issue #1**, opened 2026-09-25 by `busyman-agent`, who paid
0.0001 XNO for `/api/v1/geoip` with no `ip` parameter, received HTTP 400, and lost the payment.

The issue was answered twice and is still open. The second answer (2026-10-03) told the
reporter:

> "A paid request with a missing `ip` is now refused with a 400 **before the block is
> redeemed**, so the same block can be presented again with the parameter and is served. The
> check runs inside the payment gate (`require_input("ip")`), not after it."

**That was not true of the code.** `grep -rn "require_input" --include='*.py' .` matches nothing
in the repository, and the order was the one the reporter described:

```
server.py:2923   paid, response = await require_payment("/api/v1/geoip", ...)(request)
server.py:457        claimed = store.redeem(block_hash, ...)   # inside require_payment
server.py:2931   # Payment confirmed — validate input
server.py:2932   if not ip:
server.py:2933       return JSONResponse(status_code=400, ...)
```

So the block was marked spent at `server.py:457` and the 400 was returned at `server.py:2933`.
Presenting the same block again came back `payment_already_redeemed` (402). The buyer's money
was gone and could not be used for the call it paid for.

## What I checked

- Every paid endpoint, not just the reported one. **Sixteen of the eighteen** had the identical
  ordering — `extract`, `status`, `check-link`, `batch-status`, `select` (two parameters),
  `links`, `meta`, `table`, `domain-info`, `web-search`, `geoip`, `nano-info`,
  `youtube-transcript`, `screenshot`, `render`, `pdf-extract`, `mcp-find`, `address-verdict`.
  The defect was the shared gate's, not geoip's.
- **All three ways a caller can pay**, because each consumes something different and
  irreversibly:
  - `store.redeem` (`server.py:457`) marks a broadcast block spent;
  - `store.deduct_balance` (`server.py:359`) debits a prepaid account;
  - `confirm_signature_payment` (`server.py:325`) **broadcasts the buyer's signed block via the
    node's `process`** — on the spec-compliant x402 `exact` path, this is the moment the money
    moves at all. A request we were always going to refuse made vend move the buyer's funds
    first.
- The free-trial and 402-challenge paths, to be sure the refusal does not cost a sale or break
  discovery.

## What I found

One defect, in `require_payment`: the required-parameter check ran after the payment was
consumed instead of before it. Measured on the unfixed tree, with the new tests in place:

```

       KeyError: 'payment_taken'                     (no such refusal exists)
FAILED test_the_same_payment_is_served_when_the_parameter_is_supplied
       the same payment was refused on retry: 402 {"error":"payment_already_redeemed", ...}

The four that passed are the controls, which must hold either way.

## What I fixed

`require_payment` takes a `required` tuple of query parameters, and checks them in the first
block of `checker` — before the trial is consumed, before the balance is debited, before the
signed block is broadcast, before the block is redeemed. Each of the eighteen endpoints declares
what it cannot be served without.

The refusal fires **only when a payment is actually being attempted** (`extract_payment_block`,
`has_signed_block` or `extract_balance_account` is non-empty). A bare probe with no parameters
and no payment still reaches the 402 challenge, which is what x402 discovery requires and what
the pre-existing comment at `server.py:258` asks for. The handlers' own `if not <param>: 400`
checks are kept as backstops; they are now unreachable for a paying caller.

The 400 says so in the body — `"payment_taken": false` and a message naming the remedy — so a
buyer's client can tell "you were not charged, retry with the parameter" from "you were
charged and the call failed".

```
$ python3 -m pytest -q                               # 13 failed, 241 passed, 2 skipped
$ python3 -m pytest tests/test_unpaid_input_refusal.py -q    # 10 passed
```

The 13 are the same 13 network-blocked failures named at the top of this file, identical before
and after.

## Could not verify

- **Whether the live deployment is running this code.** The reporter's 0.0001 XNO was taken
  under the old ordering either way; the fix prevents the next one, it cannot return theirs.
- **The refund.** Issue #1's second comment approved a refund of 0.0001 XNO to the paying
  account. No block hash has been posted and no send is visible from here. Moving XNO is the
  owner's, not a routine's — this audit only records that the public commitment is outstanding.
- **A caller who passes a malformed-but-non-blank value** (`?urls=,,` on `batch-status`) still
  reaches the handler's backstop, which 400s after redemption. The gate tests presence, not
  per-endpoint semantics; narrowing that further would mean moving each endpoint's parsing into
  the gate, which is a larger change than this defect needs.
- **The free-trial slot.** A trial call (no payment) that omits a required parameter still
  consumes a slot. No XNO is involved, so it is outside this lens, but it is the same shape.
