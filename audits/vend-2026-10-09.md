# vend — audit 2026-10-09

Fourth audit, same lens: can an agent pay — or in this repository's case **get paid** — in XNO
with this code today without being hurt? Vend is the seller side of the 402, so the question
here is whether a buyer can be served without really paying, and whether an honest buyer can
lose a payment.

## What I checked

- `nano_verify.py` end to end (587 lines): both settlement dialects, the 402 challenge builder,
  the amount and destination checks, the header parsers.
- `server.py`'s `require_payment` gate (`server.py:250-536`) — the order in which a payment is
  verified, redeemed and served, and what a refusal costs the buyer.
- `store.redeem` as the replay guard, and the `required`-parameter pre-check that was added for
  issue #1.
- The suite: `166 passed, 10 failed` on `main` before any change. **All ten failures are
  network-dependent** and identical before and after this branch — five `test_wiki_summary`,
  four `test_paid_response` live-endpoint tests, one `test_cdp_verify` keyless probe. This
  container's proxy answers `403` for the external hosts, as the three previous audits also
  recorded.

## What I found and fixed

**An on-ledger send that the node has not confirmed was accepted as a payment.**

`block_info` reports `confirmed` in the same response `verify_payment` already reads, and
neither `verify_payment` (`nano_verify.py:412`, the `X-PAYMENT` dialect) nor
`wait_for_confirmation` (`nano_verify.py:215`, the `PAYMENT-SIGNATURE` dialect) read it.
`wait_for_confirmation` treated "`block_info` returned contents" as confirmed, which its own
docstring already contradicted.

While a send is unconfirmed, the account that signed it can publish a second block off the same
`previous` — a fork — and only one of the two survives the representatives' vote. So a payer
could hand Vend the hash of the fork that pays Vend, be served, and keep the money.

This is **the third time this repository's audits have found it** (2026-10-01 finding 3,
2026-10-05 "the one finding that still needs a decision"). Both earlier passes left it to the
owner on the same reasoning: requiring confirmation "risks refusing legitimate sub-second
callers". That reasoning rested on a premise this pass checked and found not to hold:

> `require_payment` calls `verify_payment` **before** `store.redeem` (`server.py:494` against
> `server.py:513`). A refused block is therefore **not marked spent**, and the same hash is
> served on a retry.

So the refusal is free to the honest buyer — one retry, no payment lost — while serving the
unconfirmed hash is not free to the seller. That is what changed the answer, not a new appetite
for strictness.

The fix refuses **only on an explicit negative**:

- `verify_payment` refuses when the node says `confirmed` is `"false"` (Nano's RPC sends the
  string; a JSON-typed proxy may send the boolean). The buyer is told no payment was taken and
  to present the same hash again.
- `wait_for_confirmation` keeps polling inside **its existing timeout budget** instead of
  returning on the first on-ledger sighting — the signature dialect has already broadcast the
  block, so waiting out a sub-second confirmation serves that buyer better than refusing them.
- A response carrying **no** `confirmed` field — an RPC proxy that drops it, an older node — is
  "we do not know" and keeps exactly the behaviour it had before this check existed. This
  matters: it is why a field this container cannot observe against a live node **can never take
  the paywall down**.
- The amount check still runs first, so a short unconfirmed payment is still refused for being
  short.

Nothing else moved: no amount, no destination, no rounding, no key path. The change only ever
narrows what is accepted.

## How to verify it

```
$ .venv-audit/bin/python -m pytest -q tests/ test_paid_response.py test_cdp_verify.py test_balance.py
180 passed, 10 failed      # the same 10 network failures as main; 166 passed before
```

`tests/test_payment_confirmation.py` is 14 laws. With `nano_verify.py` **alone** reverted to
`main`, **6 fail**:

```
6 failed, 8 passed
  test_an_unconfirmed_block_is_refused
  test_an_unconfirmed_block_is_refused_as_a_json_boolean
  test_the_refusal_says_no_payment_was_taken
  test_wait_for_confirmation_does_not_return_on_an_unconfirmed_sighting
  test_wait_for_confirmation_returns_once_the_vote_lands
  test_the_predicate_reads_only_an_explicit_negative
```

The other **8 are controls that must hold either way**, so the refusal cannot quietly cost a
working sale: a confirmed block is accepted; a response with no `confirmed` field is accepted;
an unreadable value (`""`, `"   "`, `"unknown"`, `None`, `0`, `[]`, `{}`) is accepted; a short
payment is still refused for being short; a wrong destination is still refused; the amount and
payer are still reported on the refusal; `wait_for_confirmation` still returns with no
`confirmed` field and still fails fast on a rejected block.

**Five mutation controls, all killed:**

| mutation | killed by |
|---|---|
| drop the boolean form of the negative | the JSON-boolean law (5 fail) |
| fail **closed** on an unreadable field | the three fail-open controls (4 fail) |
| `wait_for_confirmation` returns on first sighting again | the two wait laws (2 fail) |
| `verify_payment` skips the check | the three refusal laws (3 fail) |
| hoist the check above the amount check | the short-payment ordering law (1 fail) |

## Found, not fixed — still the owner's

- **The prepaid-balance credential hole** (2026-10-01 finding 2). `X-BALANCE` names an account
  with no proof the caller controls it, so anyone who learns a depositor's address can spend
  their prepaid XNO. Unchanged here: it cannot be fixed without choosing what the credential
  should be (a bearer token issued at top-up, or a Nano signature over a server nonce), and
  both change the documented interface. Still the one open product decision on this repository.
- **`confirm_signature_payment`'s docstring oversells step 2.** It says it will "fast-fail on
  destination mismatch and on a bad decrement amount", but nothing calls `block_decrement_amount`
  before broadcasting — it is dead code, and the amount is only checked afterwards by
  `verify_payment`. The outcome is still correct, so this stays a note rather than a change.
- **`raw_to_xno` carries a raw amount through a float** (`val / 1e30`, `:.6f`,
  `nano_verify.py:77`). Display only — it builds message strings and decides nothing — so a
  sub-microXNO amount prints as `0.000000`. Not on the decision path; left alone rather than
  churned.
- **A committed virtualenv.** `.venv-audit/` is tracked (most of this repository's 5,954 files).
  Removing it is a repository-hygiene change, not a defect on the XNO path, so it is not touched.

## What I could not verify

- **Whether `rpc.nano.to` returns `confirmed` on `block_info`.** No socket reaches it from this
  container (proxy `403`), as in all three previous audits. This is exactly why the check refuses
  only on an explicit `"false"` and treats an absent field as today's behaviour: if that endpoint
  turns out never to send the field, this change is a no-op rather than an outage. The Nano node
  RPC documents the field and sends it as a string.
- **The live deployment's behaviour.** No endpoint on `paypercall.dev` was reached, so nothing
  above rests on observed production traffic.
- **The ten network-dependent failures** were confirmed identical before and after, but their
  underlying endpoints were not exercised against the real hosts.
