# vend — audit 2026-10-01

Scope: can an agent pay for a Vend endpoint in XNO today, and can it be charged
wrongly or served for free? Only the XNO path was read.

## Checked

- `uv sync --group dev` then `uv run python -m pytest -q`: **210 passed, 13 failed,
  2 skipped** before any change. All 13 failures are tests that fetch live URLs
  (`test_paid_response.py`, `test_links_endpoint.py`, `tests/test_wiki_summary.py`,
  `test_pdf_extract.py`, `test_cdp_verify.py`); this audit container has no outbound
  access to those hosts, so they are environmental, not defects. The same 13 fail
  identically after the change.
- `nano_verify.py`: `_price_to_raw`, `parse_block_hash`, `check_block_exists`,
  `verify_payment`, `confirm_signature_payment`, `wait_for_confirmation`,
  `build_402_challenge`.
- `server.py`: `require_payment` end to end — trial path, `PAYMENT-SIGNATURE`
  acceptance, prepaid-balance path, the 402 challenge, verify, redeem.
- `store.py`: `redeem`, `top_up`, `balance_of`, `deduct_balance`.
- Amount handling: prices are read from the environment as floats but converted
  through `Decimal(str(price)) * 10**30`, which is exact for every price the server
  takes. No float reaches a raw amount. Replay is blocked by the UNIQUE constraint
  on `block_hash` in both `redeem` and `top_up`, and the redemption is recorded
  before the work is done.

## Found

### 1. The amount check could be skipped entirely — fixed in this PR

`nano_verify.py:433` (before the fix) wrapped the price comparison in
`try: ... except (ValueError, TypeError): pass`, and the code after the `except`
set `result["valid"] = True`. Any ledger response whose `amount` did not parse as
an integer therefore passed verification *with the price never compared*:

```
amount=''           -> valid True  "Payment verified: unknown XNO received"
amount=None         -> valid True  "Payment verified: unknown XNO received"
amount='0'          -> valid False "Payment too small"   (the only case checked)
```

`check_block_exists` returns the third-party RPC's JSON verbatim, so an RPC or
proxy that answers HTTP 200 with an empty, null or missing `amount` — and no
`error` key — bought an unlimited number of paid calls for nothing. A
misconfigured `VEND_PRICE_*` (empty string) did the same thing.

Fixed: both sides are parsed before the comparison, and an amount that cannot be
read is refused ("payment not verified") instead of accepted. Six regression tests
in `tests/test_verify_amount.py`; four of them fail on `main` and pass with the fix.

### 2. `X-BALANCE` spends a prepaid balance with no proof of ownership — NOT fixed, needs a decision

`server.py:355-379`. The prepaid-balance path takes the account to charge straight
from the `X-BALANCE` request header (`extract_balance_account`, `server.py:216-230`,
format check only) and calls `store.deduct_balance(balance_account, price_raw)`. A
Nano address is public: it is on the ledger in the payer's own top-up block, it is
recorded as `source` in Vend's own redemption rows, and `GET /api/v1/balance?account=nano_...`
discloses any account's balance for free.

So anyone who knows an agent's address can set `X-BALANCE: <that address>` and draw
paid calls until the victim's prepaid XNO is gone. The depositor gets nothing for it.

This is not fixable without deciding what the credential should be (a bearer token
issued once by `POST /api/v1/balance/top-up`, or a Nano signature over a server
nonce). Both change the documented interface, so this audit reports it rather than
picking one. Until then the honest mitigation is to stop advertising prepaid
balances (`server.py:407`, `server.py:1584`, `server.py:1923`, `llms.txt`).

### 3. Confirmation is presence on the ledger, not `confirmed: true` — observation only

`wait_for_confirmation` (`nano_verify.py:212-236`) treats "`block_info` returned
contents" as confirmed, and the `X-PAYMENT` path does not call it at all. The node
reports `confirmed` in the same response. A payer who forks two sends off one
frontier can hand Vend the hash of the fork that pays Vend and be served before the
network settles the other one. The current behaviour is deliberate and documented in
the docstring, and tightening it risks refusing legitimate sub-second callers, so it
is left to the owner.

## Could not verify
